# Missing Kanji Discovery And Export Implementation Plan

> **For Hermes/Codex:** Execute this plan one goal at a time. Start each section with `/goal Goal N: <title>` and require Codex to produce the stated design artifact, tests, and verification evidence before implementing it. Do not combine the provider-write goals with the read-only discovery goals in one change.

**Goal:** Add a first-class **Missing Kanji** feature beside **Games** that scans every kanji represented anywhere in the user's AnkiDroid collection, compares that inventory with Kani's ranked offline dictionary, lets the user choose a frequency range, and can either add selected missing kanji to Kani's study queue or create an idempotent Anki deck from them.

**Architecture:** Keep collection-wide discovery separate from Kani's existing configured-note-type sync so this feature cannot change import, retirement, or scheduler semantics accidentally. Put deterministic set comparison, frequency filtering, selection, and action planning in pure Kotlin; add narrow Android adapters for AnkiDroid reads/writes, a local source for dictionary-origin Kani queue items, and a Compose route hosted under Home. Build the read-only report first, then Kani queue admission, then Anki deck creation behind capability checks.

**Tech Stack:** Kotlin, Android ContentResolver/AnkiDroid provider, Jetpack Compose, SQLite, Kani's offline `kanji_dictionary.db` (KANJIDIC2 + Jiten ranks), JUnit, Android instrumentation tests, fake AnkiDroid provider, EN/JA centralized copy.

---

## Product contract and assumptions

1. **“In Anki” means all note fields in the live AnkiDroid collection**, across all note types and decks, not only the configured Kiku model and not only currently active cards. Tags, deck names, template HTML/CSS, and deleted notes do not count. Suspended notes do count.
2. HTML, entities, Anki sound/media markers, and furigana markup must be normalized before calling the existing `TextUtil.extractKanji`; discovery stores only unique Unicode kanji literals, never note text.
3. **“Frequency” means Jiten frequency rank.** Rank `1` is most frequent. The UI should offer understandable presets (for example Top 1,000 / Top 2,000 / Top 3,000 / Top 5,000 / Custom) plus a custom inclusive min/max range. Unranked KANJIDIC2 entries are excluded by default and may be included only through an explicit “include unranked” advanced choice.
4. The baseline universe is the bundled dictionary, currently 13,108 KANJIDIC2 entries, 8,031 of which have Jiten ranks (observed in the current asset). Tests must use fixtures rather than pinning production counts forever.
5. The report is `eligible dictionary kanji - collection kanji`. Results are sorted by Jiten rank ascending, then literal; duplicate appearances across notes/fields/decks collapse to one literal.
6. The feature must not silently create thousands of reviews. Both destinations require explicit selection and a confirmation summary. “Select all in range” is allowed and must remain performant for roughly 5,000–8,000 rows.
7. Adding to Kani creates a durable **dictionary-origin source**, not a fake Anki note or a write directly into `study_items`. The normal seeding/reconciliation path remains the only authority that creates scheduler items.
8. Creating an Anki deck is additive and idempotent. It must never rewrite existing user notes, create duplicate notes on retry, or touch Anki scheduling state. If the installed AnkiDroid/API cannot support safe note/deck creation, the UI must explain that and offer a shareable UTF-8 CSV fallback; do not pretend an `.apkg` was created.
9. Collection note text is processed in memory and is not persisted or logged. Persist only kanji membership, scan metadata/counts, selected frequency settings, and destination receipts needed for idempotency/recovery.
10. This feature is next to Games on Home, not inside Games and not a new bottom-navigation destination.

## Delivery sequence

The minimum useful release is Goals 0–5: a trustworthy read-only Missing Kanji report. Goal 6 adds Kani queue admission. Goals 7–8 add direct Anki deck creation/fallback. Goal 9 closes integration, accessibility, performance, and provider verification.

## Risks and tradeoffs

- **Provider compatibility:** Collection-wide enumeration and direct writes differ across AnkiDroid versions. Goal 0 is a hard prerequisite; CSV is the safe fallback.
- **Scheduler semantics:** Dictionary-only kanji lack a real vocabulary example. Goal 6 must explicitly preserve the two-core model rather than smuggling synthetic evidence into it.
- **Scale:** A 5,000-row report is reasonable only with set-based analysis, range SQL, paging/lazy UI, and batched writes.
- **Definition of coverage:** “Appears anywhere in any note field” may count a kanji from an explanatory sentence the learner does not regard as studied. The UI should state this definition; a future deck/note-type scope filter can be added only after evidence that it is needed.
- **Frequency data:** Jiten has 8,031 ranked entries in the current asset, not every KANJIDIC2 literal. Unranked handling must be explicit and cannot be described as low frequency.
- **External side effects:** Anki writes cannot be globally transactional. Idempotent source IDs, per-item receipts, partial summaries, and resumable batches are mandatory.
- **Privacy:** A collection-wide scan touches more content than current configured-model sync. Streaming, aggregate-only persistence, and sanitized diagnostics are non-negotiable.
